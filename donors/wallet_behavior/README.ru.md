# copytrade — копитрейд-бот для Solana

Следит за **списком кошельков** через Solana RPC, распознаёт их свапы **по
изменению токен-балансов** (а не по конкретной программе — ловятся Jupiter,
Raydium, pump.fun, PumpSwap, Meteora и любой другой агрегатор) и зеркалит их.

Два режима исполнения за одним интерфейсом:

| | `DEMO_MODE=true` (по умолчанию) | `DEMO_MODE=false` |
|---|---|---|
| Что делает | считает PnL виртуально | отправляет реальные свапы через Jupiter |
| Приватный ключ | не нужен и не читается | обязателен, только из окружения/файла |
| Риск | нулевой | **настоящие деньги** |

> ⚠️ **Живой режим не запустится случайно**: нужен явный
> `LIVE_I_UNDERSTAND_THE_RISK=true`, иначе бот падает на валидации конфига.
> Перед первым включением прочитайте [«Живая торговля»](#живая-торговля) целиком.

## Установка

Нужен Python 3.11+ (проверено на 3.14).

```bash
pip install -r requirements.txt
```

`aiohttp`, `websockets`, `colorama` (цвета в консоли Windows), `python-dotenv`.
`solders` нужен **только** для живой торговли — демо импортирует его лениво и
без него работает.

## Настройка

Конфиг берётся из двух источников, переменные окружения перекрывают JSON:

```bash
cp .env.example .env
```

Минимум, который надо заполнить:

```ini
RPC_HTTP_URL=https://rpc.ankr.com/solana/<YOUR_KEY>
RPC_WS_URL=wss://rpc.ankr.com/solana/ws/<YOUR_KEY>
TARGET_WALLETS=АДРЕС1=смартмани,АДРЕС2=инсайдер,АДРЕС3
MIN_BUY_USD=50
POSITION_SIZE_SOL=0.5
DEMO_MODE=true
```

Если нужны остальные ручки — скопируйте `config.example.json` в `config.json`,
там перечислены все параметры со значениями по умолчанию. `.env` и `config.json`
уже в `.gitignore`.

### Список кошельков

В `.env` — через запятую, имя после `=` (необязательно, но с ним логи читаются):

```ini
TARGET_WALLETS=7xKX...aBc=смартмани,9pQr...Zed=инсайдер,4mNt...Uvw
```

В `config.json` — списком, элемент строкой или объектом:

```json
"TARGET_WALLETS": [
  {"address": "7xKX...aBc", "name": "смартмани"},
  "9pQr...Zed=инсайдер",
  "4mNt...Uvw"
]
```

Разделители списка — запятая, точка с запятой и перенос строки. Пробел
разделителем **не** считается: имя кошелька бывает из двух слов.

Без имени кошелёк получает автоимя `кошелёк №N` по позиции в списке. Дубликаты
и адреса, не похожие на base58, отбиваются на старте. Старое односкошелёчное
`TARGET_WALLET` тоже работает и тоже разбирается как список — если весь набор
адресов вставлен в него, кошельки разберутся все, а не только первый.

Если после `=` в имени окажется ещё один адрес (значит, список склеился на
неподдерживаемом разделителе), бот **не стартует**: молча следить за одним
кошельком вместо четырёх — дороже, чем упасть на старте. Сколько кошельков
реально подхвачено, видно в строках `[STARTUP]` и `[WALLET]`:

```
[STARTUP] ДЕМО (paper trading): кошельков 4, ...
[WALLET] №1 смартмани: 7xKX...aBc (курсор ...)
```

Все кошельки живут на **одном** WebSocket-соединении: `logsSubscribe`
принимает один адрес на подписку, но подписок в соединении может быть много.
Поллинг-курсор при этом свой у каждого кошелька — `getSignaturesForAddress`
работает по конкретному адресу, общий курсор терял бы транзакции.

### Параметры

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `RPC_HTTP_URL` | — | HTTP-эндпоинт RPC (обязателен) |
| `RPC_WS_URL` | — | WebSocket для `logsSubscribe`. Пусто → только поллинг |
| `TARGET_WALLETS` | — | Список отслеживаемых кошельков (обязателен) |
| `MIN_BUY_USD` | `50` | Покупки цели дешевле этого порога не копируем |
| `POSITION_SIZE_SOL` | `0.5` | Наш размер входа. Не зависит от размера цели |
| `DEMO_MODE` | `true` | `false` → живая торговля, см. отдельный раздел |
| `TREAT_TRANSFER_AS_SELL` | `false` | Считать вывод токена на другой кошелёк продажей |
| `CLOSE_ON_TARGET_BALANCE_ZERO` | `true` | Баланс ведущего обнулился любым способом → закрываем позицию |
| `ALLOW_REENTRY` | `true` | Разрешить повторный вход в токен, по которому позиция уже закрывалась |
| `MIN_SELL_FRACTION_PCT` | `10` | Не зеркалить продажи мельче этого % остатка — они копятся. `0` = зеркалить всё |

**Комиссии** (значения по умолчанию повторяют типовые настройки торговых ботов):

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `SLIPPAGE_BPS` | `2000` | Проскальзывание, 2000 bps = 20%. Уходит в Jupiter как `slippageBps` |
| `PRIORITY_FEE_SOL` | `0.0001` | Priority fee валидаторам |
| `BRIBE_SOL` | `0.0001` | Jito-чаевые |
| `PAPER_APPLY_SLIPPAGE` | `false` | Закладывать ли проскальзывание в бумажный PnL |

В демо `PRIORITY_FEE_SOL + BRIBE_SOL` списывается с каждой сделки — это прямые
расходы, без них статистика завышена. А `SLIPPAGE_BPS` по умолчанию **не**
применяется: 20% — это допуск «хуже какой цены не соглашаться», а не ожидаемый
убыток; закладывать его в каждую сделку значило бы занизить результат в разы.
Нужен пессимистичный сценарий — `PAPER_APPLY_SLIPPAGE=true`.

**Мониторинг и цены:**

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `POLL_INTERVAL_SEC` | `5` | Период поллинга `getSignaturesForAddress` |
| `POLL_IDLE_MULTIPLIER` | `6` | Во сколько раз реже поллить, пока WebSocket жив |
| `STARTUP_BACKFILL_LIMIT` | `0` | Сколько прошлых транзакций разобрать на старте. `0` = с чистого листа |
| `REORDER_WINDOW_MS` | `1200` | Окно буфера переупорядочивания (см. ниже) |
| `COMMITMENT` | `confirmed` | Уровень подтверждения |
| `JUPITER_API_KEY` | — | Только из окружения. Без ключа Jupiter даёт ~0.5 req/s |
| `FALLBACK_SOL_PRICE_USD` | `0` | Аварийный курс SOL, если все источники цен легли |

**Логи и вывод:**

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `LOG_DIR` | `data/logs` | Каталог логов; на каждый запуск создаётся свой файл |
| `LOG_KEEP_RUNS` | `30` | Сколько прогонов хранить, старые удаляются на старте |
| `STATS_INTERVAL_SEC` | `300` | Период автоматической печати сводки |
| `SUMMARY_FILE` | `data/summary.txt` | Куда дублировать сводку текстом; пусто — не писать |
| `LOG_LEVEL` | `INFO` | `DEBUG` показывает и проигнорированные транзакции |
| `COLOR` | `true` | Цвета в консоли |

## Запуск

Сначала проверка окружения — она бьёт по реальному RPC и Price API:

```bash
python -m copytrade check
```

Печатает конфиг (ключи — редактированно), таблицу комиссий, список кошельков,
проверяет `getHealth` и слот, что у **каждого** кошелька есть транзакции,
**поддерживает ли провайдер `logsSubscribe`** и держит ли столько подписок в
одном соединении, и что курс SOL/USD достаётся. В живом режиме дополнительно
загружает ключ и показывает адрес, с которого будет торговать.

```bash
python -m copytrade run
```

Останов — `Ctrl+C`: бот допишет состояние, напечатает финальную сводку и
выгрузит CSV.

Остальные команды работают на остановленном боте:

```bash
python -m copytrade stats
```

```bash
python -m copytrade export
```

`stats` печатает сводку по сохранённому состоянию с текущей переоценкой,
`export` пишет `positions.csv`, `trades.csv` и `wallets.csv`.
Флаги: `--config`, `--env`, `--log-level DEBUG`, `--no-color`, `--version`.

## Логика копирования

### Ведущий (owner)

Кошельков много, позиция по токену — одна. Кто **первым** купил токен, тот
становится ведущим по этой позиции:

- Копируется только покупка ведущего.
- Покупки того же токена остальными пропускаются: `BUY_SKIPPED` с
  `rule=NOT_OWNER` и текстом «уже держим, ведущий — кошелёк №1».
- Продажи зеркалятся **только** по ведущему. Продажи остальных по этому
  токену — `SELL_SKIPPED` / `NOT_OWNER`, позицию они не трогают, даже если
  кто-то из них вышел полностью.
- После полного закрытия позиции токен снова свободен: следующая покупка любым
  кошельком открывает новую позицию с новым ведущим.

**«Первый» считается по `slot`/`blockTime` транзакции, а не по порядку
обработки ботом.** Это важно: после реконнекта или при догоне пропущенных
транзакций порядок доставки не совпадает с порядком в блокчейне. Если приходит
покупка с более ранним слотом, чем у текущего ведущего, бот перевешивает
ведущего и пишет `OWNER_REASSIGNED` (`rule=OWNER_EARLIER`).

Переназначение меняет **только атрибуцию** — кому в статистике засчитается эта
позиция. Цена входа, размер и `open_signature` остаются от фактически
исполненной сделки: мы вошли по той цене, по которой вошли, задним числом её
переписывать нельзя. После первой продажи ведущий уже не меняется.

### Покупка

Копируем, только если **все** условия выполнены:

1. Это действительно покупка — кошелёк потратил SOL/wSOL/USDC/USDT и получил SPL-токен.
2. Объём покупки ≥ `MIN_BUY_USD`.
3. По этому минту **нет открытой позиции** — копируется только первая покупка.
   Докупки самого ведущего логируются как `BUY_SKIPPED` / `TARGET_RE_BUY`.

Входим всегда на `POSITION_SIZE_SOL`, независимо от того, сколько занёс ведущий.
Цена входа берётся из самой транзакции (сколько SOL за сколько токенов); если из
транзакции цену не вывести (свап токен→токен, мульти-хоп) — из Jupiter Price API
на момент события.

### Продажа — зеркалим долю, а не количество

Когда ведущий продаёт, считается, какой процент **своего текущего остатка** он
продал, и ровно тот же процент продаётся от **нашего текущего остатка**:

```
доля = (баланс ведущего ДО транзакции − баланс ПОСЛЕ) / баланс ДО
```

Доля берётся из pre/post-балансов самой транзакции, поэтому она кумулятивна по
построению: не ломается, если ведущий докупал токен без нас, и не разъезжается,
если бот пропустил транзакцию.

Пример — ведущий купил на 3 SOL, мы вошли на 0.5 SOL:

| Действие ведущего | Его остаток | Доля | Наша продажа | Наш остаток |
|---|---|---|---|---|
| покупка | 3 000 000 | — | — | 500 000 |
| продал 750 000 | 2 250 000 | 25% | 125 000 | 375 000 |
| продал 1 125 000 | 1 125 000 | 50% | 187 500 | 187 500 |
| продал всё | 0 | 100% | 187 500 | 0 → позиция закрыта |

Если баланс токена у ведущего обнулился **любым** способом — продажей, выводом,
сжиганием — позиция закрывается (`CLOSE_ON_TARGET_BALANCE_ZERO`).

### Порог мелких продаж

Ведущий может спамить продажами по 1% — рассыпать выход на полсотни сделок.
Каждая зеркальная сделка стоит `PRIORITY_FEE_SOL + BRIBE_SOL`, и на комиссиях
уйдёт больше, чем спасёт такой выход. Продажи мельче `MIN_SELL_FRACTION_PCT`
(по умолчанию 10% остатка) не исполняются: `SELL_SKIPPED` с
`rule=BELOW_MIN_FRACTION`.

**Пропущенные доли не выбрасываются, а копятся.** Просто игнорировать мелочь
нельзя: доли считаются от остатка, и десять продаж по 1% оставят ведущему 90.4%,
а нам — 100%. Мы бы навсегда отстали. Поэтому копится произведение `(1 − доля)`,
и как только накопленное перевалит за порог, всё исполняется одной сделкой:

| Продажа ведущего | Доля | Накоплено | Что делаем |
|---|---|---|---|
| 3 000 000 → 2 850 000 | 5% | 5% | ждём |
| 2 850 000 → 2 707 500 | 5% | 9.75% | ждём |
| 2 707 500 → 2 572 125 | 5% | 14.26% | **продаём 14.26% нашего остатка** |

После исполнения счётчик обнуляется и копится заново. Одна комиссия вместо трёх,
а доля остатка у нас и у ведущего сходится копейка в копейку — это свойство
проверяется отдельным тестом.

**Полный выход ведущего порогом не блокируется никогда**, даже если он сливает
последний 0.5%: закрыть позицию важнее, чем сэкономить на комиссии. Накопитель
живёт в состоянии и переживает перезапуск. `MIN_SELL_FRACTION_PCT=0` отключает
порог полностью.

### Вывод токена на другой кошелёк

Отличается от свапа: токен ушёл, встречного прихода SOL/стейбла нет. Логируется
как `TRANSFER_OUT`. При `TREAT_TRANSFER_AS_SELL=true` считается продажей по
рынку; при `false` частичный вывод только пишется в лог, а полное обнуление
баланса всё равно закрывает позицию. Выводы не-ведущих — всегда только лог.

## События

Пишутся в цветную консоль, в лог-файл текущего прогона и построчным JSON в
`events_*.jsonl` (удобно грепать и потом анализировать).

| Событие | Когда |
|---|---|
| `BUY_DETECTED` | кошелёк купил токен — с объёмом в SOL и USD и ссылкой на Solscan |
| `BUY_COPIED` | вошли: сколько токенов, по какой цене, откуда цена, кто ведущий |
| `BUY_SKIPPED` | не вошли. Причина в поле `rule`: `NOT_OWNER`, `TARGET_RE_BUY`, `BELOW_MIN_USD`, `NO_PRICE`, `REENTRY_BLOCKED`, `RISK_LIMIT`, `STALE_SIGNAL` |
| `OWNER_REASSIGNED` | нашлась более ранняя покупка — ведущий перевешен (`rule=OWNER_EARLIER`) |
| `SELL_DETECTED` | продажа — сколько и какой процент остатка |
| `SELL_COPIED` | зеркалили продажу: доля, объём, реализованный PnL |
| `SELL_SKIPPED` | не зеркалили. `rule`: `NOT_OWNER`, `NOT_HELD`, `NO_DECREASE`, `BELOW_MIN_FRACTION` (мелкая продажа — накоплена в поле `pending_fraction`) |
| `POSITION_CLOSED` | итог позиции: PnL в SOL, USD и %, число частичных продаж, время удержания, ведущий |
| `TRANSFER_OUT` | вывод токена на другой кошелёк |
| `WS_UP` / `WS_DOWN` | состояние подписки |
| `FRESHNESS` | при старте живого режима: как настроена защита от покупок из прошлого |
| `TX_IGNORED` | движение балансов без торговли (виден на `DEBUG`) |

Каждая строка события несёт имя кошелька, поэтому в общем потоке видно, кто
именно сходил.

### Ширина колонок и не-латиница

Символы мемкоинов бывают китайскими (`富贵`, `月薪喵`), с эмодзи или с
комбинирующими диакритиками. `len()` для выравнивания там не годится: иероглиф
занимает **две** ячейки терминала, а комбинирующий знак — ноль. Ширина везде
считается по `unicodedata.east_asian_width`, обрезка длинных символов — тоже по
ячейкам, а не по кодпойнтам. Таблицы не разъезжаются на любом наборе символов.

## Артефакты

Всё складывается в `data/` (перенастраивается в конфиге):

| Файл | Что внутри |
|---|---|
| `state.json` | Позиции с ведущими, счётчики по каждому кошельку, курсоры, обработанные подписи. Переживает перезапуск |
| `state.bak.json` | Копия предыдущего состояния |
| `logs/copytrade_ГГГГ-ММ-ДД_ЧЧ-ММ-СС.log` | Полный лог **этого** запуска |
| `logs/events_ГГГГ-ММ-ДД_ЧЧ-ММ-СС.jsonl` | Те же события структурно, по строке на событие |
| `logs/latest.txt` | Пути к логам последнего прогона (симлинки на Windows требуют прав админа) |
| `summary.txt` | Последняя сводка текстом — то же, что раз в 5 минут уходит в консоль |
| `positions.csv` | Позиции: ведущий, вход, стоимость, реализованный/нереализованный PnL, %, холд |
| `trades.csv` | Каждая частичная продажа отдельной строкой |
| `wallets.csv` | PnL в разрезе ведущего |

Каждый запуск пишет в **свой** файл логов, имя — дата и время старта. Бот
работает сутками; смешивать прогоны в один лог значит потерять границу «до
перезапуска / после». Старые прогоны подчищаются по `LOG_KEEP_RUNS`.

CSV пишутся в `utf-8-sig` — Excel на Windows открывает их без плясок с
кодировкой.

### `summary.txt`

Консоль прокручивается и теряется, поэтому та же сводка кладётся в файл:
целиком, без ANSI-цвета, **перезаписью** — внутри всегда только последняя.
Обновляется в тот же момент, что и CSV: раз в `STATS_INTERVAL_SEC` и на
остановке бота. История не теряется — её несут `trades.csv` и `positions.csv`,
обновляемые тем же вызовом.

Запись атомарная (временный файл + `replace`): файл читают снаружи, и застать
его наполовину переписанным хуже, чем прочитать сводку пятиминутной давности.
Если файл занят (открыт в Excel), бот пишет предупреждение в лог и продолжает
работу — на торговлю это не влияет.

Смотреть вживую:

```bash
Get-Content -Wait data/summary.txt
```

`SUMMARY_FILE=""` отключает файл. Путь печатается при старте и в `check`.

### Статистика по кошелькам

Отдельная таблица и `wallets.csv`: позиции, win rate, вложено, реализованный и
нереализованный PnL, ROI, средний холд, плюс счётчики
`buys_detected/copied/skipped` и `sells_*` по каждому адресу. Позиция
засчитывается тому, кто был её ведущим, — так демо сразу показывает, кого из
отслеживаемых выгодно копировать, а кто тянет в минус.

## Как устроено

```
monitor.py    logsSubscribe (N подписок в одном WS) + поллинг -> очередь сигнатур
   ↓
engine.py     буфер переупорядочивания -> getTransaction -> parser -> strategy -> executor
   ↓
parser.py     балансовые дельты -> WalletActivity -> список TradeEvent
strategy.py   TradeEvent -> Decision (копировать / пропустить / закрыть / сменить ведущего)
executor.py   Executor (интерфейс) + PaperExecutor (демо) + build_executor()
live.py       LiveExecutor: Jupiter quote/swap, подпись solders, отправка, подтверждение
portfolio.py  позиции, ведущий, частичные продажи, реализованный PnL
storage.py    атомарное сохранение состояния
stats.py      сводка, таблицы, CSV
prices.py     SOL/USD и цены токенов с кэшем и фолбэками
```

Несколько мест, где легко ошибиться, и что с ними сделано:

- **wSOL.** Нативная дельта SOL и дельта wSOL складываются, поэтому wrap/unwrap
  взаимно уничтожаются и не превращаются в покупку или продажу. Транзакция,
  где кроме обёртки ничего не было, помечается `WRAP_UNWRAP` и игнорируется.
- **Пропуск транзакций.** `logsSubscribe` не даёт гарантий доставки, поэтому
  поллер работает **всегда**, просто реже, пока WebSocket жив. После каждого
  переподключения делается догон через `getSignaturesForAddress` от последней
  известной сигнатуры — **свой курсор на каждый кошелёк**, с пагинацией.
- **Дубликаты.** Обработанные сигнатуры хранятся в состоянии (последние 5000) и
  переживают перезапуск. Ключ — `кошелёк:сигнатура`: одна транзакция может
  затрагивать два отслеживаемых кошелька, и это два разных события.
- **Порядок.** WS и поллер приходят вразнобой, продажа может обогнать покупку.
  Сигнатуры отлёживаются `REORDER_WINDOW_MS` и обрабатываются пачкой по
  возрастанию слота. На этом же механизме держится корректный выбор ведущего.
- **Address Lookup Tables.** Для v0-транзакций адреса из ALT приклеиваются к
  `accountKeys`, иначе индексы балансов разъезжаются.
- **Аренда ATA.** Приход токена вместе с тратой ~0.002 SOL — это не покупка,
  а создание аккаунта; порог `SOL_DUST_LAMPORTS` это отсекает.
- **Комиссия сети.** В `preBalances/postBalances` она уже вычтена из счёта
  плательщика, поэтому парсер возвращает её обратно в дельту нулевого аккаунта —
  иначе каждая транзакция выглядела бы как трата на 5000 лампортов больше.
- **Деньги.** Везде `Decimal` с точностью 40 знаков, в JSON сериализуется
  строками. `float` в расчётах PnL не участвует.
- **USD-PnL** считается честно: затраты по курсу SOL на входе, выручка по курсу
  на выходе, — то есть движение самого SOL тоже попадает в результат.

### Догон истории

Первое, что делает поллер при старте, — [`_catch_up_all("backfill")`](copytrade/monitor.py),
ещё до того, как WebSocket успеет подписаться. Для каждого кошелька берётся
курсор из `state.json` (последняя обработанная сигнатура) и запрашивается
`getSignaturesForAddress(until=курсор)` с пагинацией. Результат разворачивается
(RPC отдаёт от новых к старым) и **льётся в ту же очередь, что и WebSocket** —
движок не отличает догон от реального времени, только по полю `source`.

Поэтому после простоя в логе видно, как бот за секунды проигрывает часы
истории: `холд 5s` — весь цикл вход-выход целиком лежал в бэклоге; `холд 5h26m` —
позиция висела ещё до выключения, а её продажа приехала в догоне. Цены берутся
из самих транзакций (`цена: tx`), поэтому демо-PnL исторически корректен, а не
посчитан по текущему рынку.

То же самое происходит после каждого реконнекта WS — `_catch_up_all("reconnect")`.
Пока WS жив, поллер всё равно опрашивает RPC каждые
`POLL_INTERVAL_SEC × POLL_IDLE_MULTIPLIER` (по умолчанию 30 с).

⚠️ **Потолок догона — 10 страниц × `SIGNATURE_FETCH_LIMIT` = 10 000 транзакций
на кошелёк.** Если разрыв больше, в лог падает предупреждение «разрыв больше
10000 транзакций», и часть истории теряется. При активной цели и простое в сутки
в это можно упереться.

В живом режиме догон **не приводит к покупкам** — см. «Свежесть сигнала».

### Цены

SOL/USD: Jupiter → CoinGecko → Binance → `FALLBACK_SOL_PRICE_USD` → последнее
известное значение. Цены токенов — Jupiter Price API v3, батчами до 50 минтов,
кэш 30–60 с. **Без API-ключа Jupiter ограничивает ~0.5 запроса в секунду** —
поэтому лимитер по умолчанию 0.4 rps и агрессивное кэширование. Если следите за
несколькими активными кошельками, стоит завести ключ и положить в
`JUPITER_API_KEY` (**только** переменной окружения — в `config.json` бот его не
примет).

## Живая торговля

`DEMO_MODE=false` включает `LiveExecutor`: реальные свапы через Jupiter Swap
API, подпись локальным ключом, отправка в сеть.

### Ключ

Только из окружения или из файла **вне репозитория**:

```ini
WALLET_PRIVATE_KEY=base58_или_json_массив_64_байт
# или
WALLET_PRIVATE_KEY_FILE=C:\путь\вне\репозитория\key.json
```

В `config.json` ключ положить нельзя — загрузчик отказывается стартовать, если
видит там `WALLET_PRIVATE_KEY` или `JUPITER_API_KEY`: этот файл слишком легко
закоммитить. Ключ не попадает ни в логи, ни в текст исключений (ошибки разбора
поднимаются через `raise ... from None`, чтобы значение не всплыло в трейсбеке).
Необязательный `WALLET_PUBLIC_KEY` сверяется с адресом из ключа — защита от
«загрузил не тот файл».

### Предохранители

| Ключ | По умолчанию | Смысл |
|---|---|---|
| `LIVE_I_UNDERSTAND_THE_RISK` | `false` | Без `true` живой режим не стартует |
| `MAX_OPEN_POSITIONS` | `5` | Больше открытых позиций бот не наберёт |
| `MAX_DAILY_LOSS_SOL` | `1` | Порог по **чистому** реализованному PnL за текущие локальные сутки |
| `SKIP_BUYS_BEFORE_START` | `true` | Не копировать покупки, случившиеся до старта бота |
| `MAX_SIGNAL_AGE_SEC` | `60` | Не копировать покупки по сигналам старше N секунд; `0` — не проверять |
| `MIN_WALLET_BALANCE_SOL` | `0.02` | Неснижаемый остаток на комиссии |
| `LIVE_CONFIRM_TIMEOUT_SEC` | `90` | Сколько ждём подтверждения |
| `LIVE_SEND_MAX_RETRIES` | `3` | Повторы отправки **той же самой** подписанной транзакции |
| `LIVE_SKIP_PREFLIGHT` | `true` | Отправка без предварительной симуляции — быстрее, но провальный свап всё равно оплатит комиссию |

Оба лимита проверяются **перед каждой покупкой**; при срабатывании пишется
`BUY_SKIPPED` с `rule=RISK_LIMIT` на уровне `WARNING`. Дневной убыток считается
по частичным продажам с начала локальных суток и **сальдируется**: позиция,
открытая вчера и распроданная сегодня, попадает в сегодняшний лимит целиком, а
прибыльные сделки гасят убыточные. В демо лимиты не применяются намеренно — кап
на число позиций исказил бы статистику, ради которой демо и запускается.

Продажи лимитами не блокируются никогда: выйти из позиции должно быть можно
всегда, даже когда лимит убытка уже исчерпан.

### Свежесть сигнала (только живой режим)

Поллер при старте догоняет всё, что произошло, пока бот стоял (см. «Догон
истории»). Демо на этом строит точную статистику — и это правильно. На реальных
деньгах то же самое означает: после двухчасового простоя бот скупит токены,
которые цель за эти два часа уже купила **и слила**, и тут же их продаст,
заплатив две комиссии за каждый.

Поэтому в живом режиме покупка копируется, только если сигнал свежий:

| Условие | Что делает |
|---|---|
| `block_time < момента старта бота` | `BUY_SKIPPED`, `rule=STALE_SIGNAL` (при `SKIP_BUYS_BEFORE_START=true`) |
| возраст сигнала > `MAX_SIGNAL_AGE_SEC` | то же — закрывает дыру при обрыве WS **посреди** работы, а не только на старте |
| у транзакции нет `blockTime` | тоже пропуск: возраст не определить, а деньги настоящие |

**Продажи не фильтруются по возрасту никогда.** Асимметрия намеренная:
опоздавшая покупка стоит денег, опоздавшая продажа их спасает. После простоя
продажа из догона — единственный способ узнать, что цель вышла, пока мы сидели
в реальных токенах. Проверено тестом `test_stale_sell_reaches_the_executor`.

Выключить обе защиты сразу конфиг не даёт: `SKIP_BUYS_BEFORE_START=false` вместе
с `MAX_SIGNAL_AGE_SEC=0` — это ровно тот сценарий, ради которого проверка и
писалась. В демо ручки не действуют, там догон копируется целиком, как и раньше.

При старте живого режима текущие настройки печатаются событием `FRESHNESS`; если
обе выключены (в демо это допустимо), уровень поднимается до `WARNING`.

Идемпотентность: на каждый минт свой `asyncio.Lock` плюс множество уже
исполненных сигнатур цели — одна транзакция цели не породит две наших. Повтор
отправки шлёт **те же байты** с той же подписью, поэтому дубля в сети не будет.
Фактическая цена исполнения не берётся из quote: бот перечитывает **свою**
подтверждённую транзакцию тем же парсером и считает PnL по реальным дельтам.

### FEE_MODE — priority или jito, но не оба сразу

Jupiter принимает в `prioritizationFeeLamports` **либо** priority fee, **либо**
Jito-чаевые — не оба одновременно.

| `FEE_MODE` | Что уходит | Куда отправляется транзакция |
|---|---|---|
| `priority` (по умолчанию) | `PRIORITY_FEE_SOL` как `priorityLevelWithMaxLamports` | обычный RPC |
| `jito` | `BRIBE_SOL` чаевыми + `PRIORITY_FEE_SOL`, пересчитанный в цену за CU | `JITO_ENDPOINT` (обязателен) |
| `auto` | Jupiter решает сам | обычный RPC |

При `FEE_MODE=priority` и ненулевом `BRIBE_SOL` бот печатает предупреждение:
чаевые не отправляются. При `FEE_MODE=jito` бюджет priority fee делится на
`ASSUMED_COMPUTE_UNITS` (400 000) и передаётся как
`computeUnitPriceMicroLamports`. Отправлять транзакцию с чаевыми через обычный
RPC бессмысленно — `BRIBE_SOL` просто сгорит, поэтому без `JITO_ENDPOINT`
режим не стартует.

### ⚠️ Прежде чем включать реальные сделки

- **Живой путь ни разу не исполнял настоящую сделку.** Проверены: загрузка
  ключа, формы платежей за комиссию, реальный quote к `api.jup.ag`, сборка
  транзакции ручкой `/swap`, подпись `solders` и round-trip base64. Отправка в
  сеть и подтверждение на реальных деньгах — **не проверены**.
- **Первый запуск — на отдельном кошельке с суммой, которую не жалко**, с
  `POSITION_SIZE_SOL` вроде `0.01` и `MAX_OPEN_POSITIONS=1`. Дождитесь одной
  полной сделки (вход + выход) и сверьте цифры в `trades.csv` с Solscan.
- Прогоните демо хотя бы несколько дней и посмотрите `wallets.csv`: копировать
  стоит не всех, кого отслеживаете.
- `SLIPPAGE_BPS=2000` — это 20%. На неликвидных мемкоинах такой допуск заберут
  сэндвич-боты. Это осознанный компромисс ради проходимости, а не бесплатная
  настройка.
- Расхождение цены входа: цель зашла в свою цену, вы зайдёте в свою — на
  неликвиде разница может быть в разы. Копитрейд не воспроизводит результат цели.
- **Прочитайте `strategy.py`, `portfolio.py` и `live.py` целиком.** Это деньги:
  доверять чужим расчётам PnL, долей и комиссий без собственной проверки нельзя.

## Диагностика

| Симптом | Что делать |
|---|---|
| `check` ругается на `logsSubscribe` | Провайдер не поддерживает подписки. Бот будет работать на поллинге — уменьшите `POLL_INTERVAL_SEC` |
| Подтверждено подписок меньше, чем кошельков | Лимит подписок на соединение у провайдера. Уберите лишние кошельки или смените RPC |
| Все покупки уходят в `BUY_SKIPPED` / `NOT_OWNER` | Так и задумано: токен уже держим, ведущий другой. Кто именно — в поле `owner` |
| Все покупки уходят в `BELOW_MIN_USD` | Цели торгуют мельче порога — понизьте `MIN_BUY_USD` |
| Продажи копятся в `BELOW_MIN_FRACTION` и не исполняются | Ведущий выходит мелкими кусками. Это защита от сжигания комиссий; понизьте `MIN_SELL_FRACTION_PCT`, если готовы платить за скорость выхода |
| `NO_PRICE` в пропусках | Токен слишком свежий, Jupiter его ещё не отдаёт |
| 401 или 429 от Jupiter | Уперлись в лимит без ключа — заведите `JUPITER_API_KEY` |
| Бот «не видит» старые сделки | Так задумано: `STARTUP_BACKFILL_LIMIT=0`. Поставьте, например, `50`, чтобы разобрать историю |
| Начать статистику с нуля | Остановите бота и удалите `data/state.json` |
| Нужен лог конкретного прогона | `data/logs/` — файлы названы временем старта, последний указан в `latest.txt` |
